# 作業要領：学習コンテンツ作成で見つかった「地図の不足」の反映

学習コンテンツ（`lessons/`）を作る過程で、学習内容マップ（`data/`）の不足が `reports/lesson_map_gaps.md` に記録された。この要領は、その記録を1件ずつ判断し、根拠のあるものだけを地図に反映する作業の規則。**判断と書き方の基準は `docs/AI_MAINTENANCE_GUIDE.md`（以下「ガイド」）がすべて優先する。** 作業前にガイドの 2〜5 節、6.6、7、8.1、9〜11 節を読むこと。

## 1. 入力

- `reports/lesson_map_gaps.md`：担当するページの行（担当の割り当ては依頼文に書く）。列は「見つけたページ｜内容｜種類｜ページでの扱い｜マップの対応案」。対応案は作成担当の提案で、そのとおりにする必要はない。
- 該当する学習コンテンツ `lessons/<モジュール名>/<rid>.html`：はざまの補足（`supp-*` の囲み）と meta の `prerequisites`・`sources` に、担当が確かめた出典がある。
- `output/json/all_rows.jsonl`・`output/json/<モジュール名>.json`：行の要点・語句・出典。
- 根拠資料：`sources/text/`（取得済みのテキスト）、`sources/registry/`（取得記録）。ガイド 3.1 の根拠なら新しく取得してよい（PDF は `tools/fetch_pdf.py`、ほかは取得したテキストを `sources/text/` に保存し、`sources/registry/` に URL・取得日時を記録する）。語句の検索は `tools/find_terms.py` が使える。

## 2. 1件ごとの判断

各件について、次のどれかに決める。

| 判断 | 条件 | すること |
|---|---|---|
| 反映 | 学習指導要領の範囲内（ガイド 5.1）で、根拠を確かめられた | 変更指示ファイルに入れる |
| 対応不要 | 地図を直さなくてよい（例：履修順の違いで、ページ側の説明で足りる。すでに別の行にある） | 理由を記録 |
| 見送り | 範囲外、根拠を確かめられない、コマ数を変えないと入らない | 理由を記録。確認できなかった語は資料の `LIMITATIONS` に追記 |
| 要確認 | ガイド 11 節の「利用者に確認すること」に当たる | 変更せず、報告に書く |

判断の目安：

- **欠落（どの行にもない内容）**：前提として必要で、範囲内なら、最も自然な行（先に学ぶ行を優先）の要点に書き足す。解説に明記がない内容を足した行は、要点の内容の † として `mark="†"` にする（すでに † なら そのまま）。語句として足すときは 5.2 の B・C の出典が必要。
- **語句**：出典の本文で確かめ、要点末尾の「主な語句：…。［語句：S番号］」に加える。新しい出典は `SOURCES` に追加。地理・歴史総合・世界史探究は対応表（`TEXTBOOK_TERMS` など）を直接編集する（ガイド 6.6 の注意）。
- **要点の明記**：その行の要点に書き足す。解説の扱いの程度（「触れる」など）に合わせる。
- **履修順**：多くは対応不要。必要なら後の行の要点に「〜の基本に触れる」と最小限を書く。
- **出典不足**：新しい公開資料で確かめられたときだけ反映。見つからなければ見送り。
- **表現・範囲の不明確・順序**：解説の記述に合わせて要点や並びを直す。並べ替えは rid を変えず、コマ数・単元の配当を保つ。

## 3. 守ること

- ガイド 2 節の不変条件（コマ数、網羅、rid、印、出典、† を削らない、範囲外を載せない、利用者の決定事項）を崩さない。**行の追加・削除は原則しない**（要点の書き足しで対応する）。どうしても必要なら要確認にする。
- 要点の長さは「主な語句」と出典の印を除いて 220 字を目安にするが、必要な内容を削らない（超える理由を記録に書く）。
- **学習コンテンツのある行**（`lessons/` にページがある rid）の `title`・`basis`・`exam` は変えない（ページの meta と一致しなくなる）。その行に主な語句を足すときは、その語がページの本文にあることを確かめる（なければ語句を足さず、報告に書く）。ページは編集しない。
- 担当外の資料（`data/` のほかのモジュール）、`reports/lesson_map_gaps.md`、`lessons/`、共通ツール（`tools/*.py`）は編集しない。語句の照合スクリプト `tools/checks/<担当モジュール>_*.py` が固定の語句リストを持つ場合は、足した語句をそのリストに加えてよい。
- `tools/rebuild_all.py` と `tools/export_json.py` は実行しない（共有ファイルを書き換えるため。取りまとめ役が最後に実行する）。

## 4. 反映の手順

1. 変更指示ファイルを `reports/map_fix/<担当名>_changes.json` に作る（ガイド 7 節の形式。各変更に `reason` と `evidence`（資料名＋ページ・節＋短い引用）を付ける）。
2. `python tools/apply_changes.py reports/map_fix/<担当名>_changes.json --dry-run` で差分を確かめてから、`--dry-run` なしで反映する（資料ごとの生成と検証が自動で走る。「検証すべて OK」を確かめる）。対応表の直接編集をしたときは `python tools/build_md.py data.<モジュール名> output/<出力名>.md` で検証する（出力名は `tools/rebuild_all.py` の `OUTPUTS`）。
3. `python tools/checks/run_all.py` で語句の照合が NG 0（既知の「世阿弥」のルビの件を除く）。
4. Windows・PowerShell では、`python -c` に波かっこや引用符を含むコードを渡すと壊れやすい。自分用のスクリプトは `tools/worker/mapfix_<担当名>_*.py` に保存して実行する。Google ドライブ上では編集直後に古い内容が読まれることがあるので、数秒待って再確認する。

## 5. 記録と報告

- `reports/map_fix/<担当名>.md`：担当した全件の判断の表（見つけたページ｜内容｜判断｜変更した行と変更の要約｜根拠）。
- 変更した資料ごとに `reports/review/<モジュール名>.md` にガイド 8.1 の形式で追記する（作業名「学習コンテンツ作成で見つかった不足の反映（2026-09-29）」）。
- 取りまとめ役への報告（日本語）：結論（反映・対応不要・見送り・要確認の件数、検証結果）、主な変更、判断に迷った点、学習コンテンツのページに影響する点（語句を足した行にページがある場合など）。
